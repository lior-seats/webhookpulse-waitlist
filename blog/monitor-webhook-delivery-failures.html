How to Monitor Webhook Delivery Failures: Stripe, GitHub, Twilio (2026 Guide)

September 2026 · 9 min read

Webhooks are the backbone of modern SaaS integrations. They let Stripe tell you a payment succeeded, GitHub notify you of a new PR, and Twilio confirm a message was delivered. When they work, they're invisible infrastructure. When they fail, the consequences range from annoying (a missing notification) to catastrophic (a customer paying but not getting access).

This guide covers practical patterns for monitoring webhook delivery across the major providers — so you know about failures before your customers do.

Why Webhook Monitoring Is Different from API Monitoring

API monitoring is active: you call an endpoint, check the response, alert on errors. Webhook monitoring is passive: you're waiting to receive calls, and you only know something is wrong when the calls stop arriving or when you go looking for failures.

This asymmetry is why most teams don't monitor webhooks well. There's no HTTP check you can run against your own endpoint to verify Stripe's delivery health. You have to either:

  1. Poll the provider's events/deliveries API
  2. Instrument your handler to track receipt and alert on gaps
  3. Use a third-party passive monitor

Per-Provider Monitoring Approaches

Stripe

Stripe provides the most complete delivery visibility of any major webhook provider. Use the Events API to find failed deliveries:

const stripe = require('stripe')(process.env.STRIPE_SECRET_KEY);

// Find all events that failed delivery in the last 24h
async function findFailedWebhooks() {
  const events = await stripe.events.list({
    delivery_success: false,
    created: { gte: Math.floor(Date.now() / 1000) - 86400 },
    limit: 100,
  });

  return events.data.map(e => ({
    id: e.id,
    type: e.type,
    created: new Date(e.created * 1000).toISOString(),
    attempts: e.request?.idempotency_key,
  }));
}

Run this as a daily cron job. If events.data.length > 0, alert your team via Slack, email, or PagerDuty.

You can also check a specific endpoint's recent delivery attempts via the Stripe Dashboard: Developers → Webhooks → [your endpoint] → Recent deliveries. Filter by status. The limitation: you have to do this manually.

GitHub

GitHub App webhooks can be monitored via the Deliveries API. For a GitHub App installation:

// List recent deliveries for a GitHub App webhook
const { Octokit } = require("@octokit/rest");
const octokit = new Octokit({ auth: process.env.GITHUB_TOKEN });

const deliveries = await octokit.request(
  'GET /app/hook/deliveries',
  { per_page: 50 }
);

const failed = deliveries.data.filter(d =>
  d.status === 'Invalid HTTP Response Code' ||
  d.status === 'Timed Out' ||
  d.redelivery === false && d.status !== 'OK'
);

if (failed.length > 0) {
  console.error(`${failed.length} failed GitHub webhook deliveries`);
}

GitHub doesn't retry failed webhooks aggressively — it tries once and marks the delivery failed. This makes monitoring even more critical.

Twilio

Twilio webhook delivery failures show up as webhookStatusCallback events (for SMS) and in the Debugger (for Voice). You can query the Twilio Error Log API:

const client = require('twilio')(
  process.env.TWILIO_ACCOUNT_SID,
  process.env.TWILIO_AUTH_TOKEN
);

// Get recent error alerts (30011 = webhook delivery failure)
const alerts = await client.monitor.alerts.list({
  errorCode: 30011,
  startDate: new Date(Date.now() - 86400000)
});

if (alerts.length > 0) {
  console.error(`${alerts.length} Twilio webhook failures in last 24h`);
}

Shopify

Shopify shows webhook delivery failures in the Partner Dashboard under Apps → [your app] → Webhooks. For programmatic access, the GraphQL Admin API exposes webhook subscription delivery status, but it's less ergonomic than Stripe's REST API.

The Gap: Cross-Provider Aggregation

Once you're running multiple integrations, you need to check Stripe, GitHub, Twilio, Shopify, and SendGrid individually. Each has a different API shape, different authentication, different retry semantics, and different alerting. The total overhead of building and maintaining this monitoring stack is measured in days — and it needs to be re-checked whenever a new provider is added.

Instrumenting Your Webhook Handler

The most reliable approach is handler-side instrumentation — you know what you received, not just what the provider thinks you received:

// Express webhook handler with receipt tracking
app.post('/webhooks/stripe', express.raw({type: 'application/json'}), async (req, res) => {
  const sig = req.headers['stripe-signature'];

  let event;
  try {
    event = stripe.webhooks.constructEvent(req.body, sig, process.env.STRIPE_WEBHOOK_SECRET);
  } catch (err) {
    return res.status(400).send(`Webhook Error: ${err.message}`);
  }

  // Track receipt immediately (before processing)
  await db.webhookReceipts.insert({
    provider: 'stripe',
    event_id: event.id,
    event_type: event.type,
    received_at: new Date(),
    status: 'received'
  });

  // Process asynchronously
  processWebhookAsync(event).catch(err => {
    db.webhookReceipts.update(event.id, { status: 'failed', error: err.message });
    alertTeam(`Stripe webhook ${event.type} failed: ${err.message}`);
  });

  // Always respond 200 immediately
  res.json({ received: true });
});

This approach captures failures even when the provider doesn't know about them (e.g., handler throws after returning 200).
