Why Stripe Webhooks Fail Silently After Retries (And How to Catch Them)

September 2026 · 7 min read

You wake up Monday morning to an angry customer: their subscription was cancelled, their order never fulfilled, their access not revoked. You check your Stripe dashboard — the payment went through. You check your server logs — nothing. The problem was silent: a webhook that failed three weeks ago and never got a second chance.

Stripe webhooks fail silently. Understanding why — and building a detection system before it costs you customers — is one of the most important things you can do in a production payment integration.

How Stripe Webhook Retries Work

When your endpoint returns a non-2xx response (or times out), Stripe queues a retry. The retry schedule looks like this:

AttemptDelay After PreviousTotal Elapsed
1st (original)—0
2nd retry~5 minutes~5 min
3rd retry~30 minutes~35 min
4th retry~2 hours~2.5 hrs
5th retry~5 hours~7.5 hrs
… up to 8 retries over ~3 days

After the last retry fails, Stripe marks the event as failed and stops trying. There is no alert. There is no email (by default). There is no Slack message. The event is simply abandoned — and your business logic never runs.

⚠️ The dangerous part

Stripe does offer email alerts for repeated webhook failures — but they only trigger after multiple consecutive failures to the same endpoint. A single critical event that fails quietly (like a customer.subscription.deleted) may never trigger an alert.

What Gets Lost When Webhooks Fail

Not all webhook events are equal. Some are informational. Others are load-bearing — your entire business logic depends on them running exactly once:

  • checkout.session.completed — Provision the product, create the account, send the welcome email. If this fails, the customer paid but got nothing.
  • customer.subscription.deleted — Revoke access, downgrade the account. If this fails, a churned customer keeps using your paid product.
  • invoice.payment_failed — Trigger dunning, pause service, notify the team. If this fails, revenue leaks silently.
  • customer.subscription.updated — Adjust quotas, change plan-based features. If this fails, the customer is on the wrong plan.

Why Webhooks Fail in Production

In development, webhook failures are obvious — you're watching the logs. In production, the failure modes are more insidious:

1. Deploy-time downtime

Your app restarts during a deploy. For 5–30 seconds, your webhook endpoint returns 502. If Stripe fires an event during that window, it queues a retry. If your next retry window falls during another deploy (increasingly likely if you deploy frequently), you can lose events across multiple retries.

2. Database connection pool exhaustion

High-traffic moments — a successful campaign, a Product Hunt launch — can saturate your connection pool. Your API returns 500 errors. Webhook handlers fail. Retries pile up and exhaust the same pool. The loop is self-reinforcing.

3. Idempotency bugs

Webhook handlers that fail partway through and don't use idempotency keys create a nightmare: the first attempt partially committed state, the retry tries to run the same logic, and you get duplicate charges, double-provisioned accounts, or worse — a handler that throws on the retry because of the partial state from the first run.

4. Third-party timeouts

Your webhook handler calls Mailchimp to add the subscriber. Mailchimp is having a slow day. Your handler times out (Stripe's timeout: 30 seconds). The event fails. Stripe retries. Mailchimp is still slow. The event eventually exhausts retries — and the subscriber is never added to your list.

Detecting Silent Failures Today

There are a few approaches teams use before they have proper monitoring:

Polling the Stripe Events API

// Check for failed events in the last 24 hours
const failedEvents = await stripe.events.list({
  delivery_success: false,
  created: { gte: Math.floor(Date.now() / 1000) - 86400 },
  limit: 100
});

if (failedEvents.data.length > 0) {
  console.error(`${failedEvents.data.length} failed events in last 24h`);
  // alert your team
}

This works, but requires a scheduled job and manual triage. You need to run it periodically, deduplicate across runs, distinguish transient failures from persistent ones, and build the alerting pipeline yourself.

Stripe Dashboard Webhook Logs

The Stripe Dashboard shows webhook delivery attempts under Developers → Webhooks → [your endpoint] → Recent deliveries. You can filter by status. But you have to check it manually — it won't alert you.

Datadog / Sentry webhook handler monitoring

If you already have APM, you can track webhook handler errors as custom metrics. This gives you alerting but requires custom instrumentation and doesn't give you the Stripe-side view (event type, retry count, payload).

The Gap: No Passive Cross-Provider Monitor

What's missing is a tool that passively watches your webhook endpoints across providers — Stripe, GitHub, Twilio, Shopify, SendGrid — and alerts you the moment delivery starts failing. Not after 8 retries over 3 days. Within minutes.

This should work without requiring you to modify your webhook handler code, add a polling job, or check any dashboard manually. It should send a Slack message, an email, or a PagerDuty alert the moment it detects delivery failures — with the event type, provider, and failure count in the alert body so you can fix it fast.

Quick Checklist: Webhook Reliability for Production

  • ✅ Return 2xx from your endpoint within 30 seconds (queue processing async if needed)
  • ✅ Implement idempotency keys — check if event was already processed before acting
  • ✅ Log every incoming event with its ID and type
  • ✅ Set up Stripe email alerts for consecutive delivery failures (Developers → Webhooks → [endpoint] → Edit → Email notifications)
  • ✅ Poll stripe.events.list({"delivery_success": false}) daily via a scheduled job
  • ✅ Monitor your webhook handler error rate via APM
  • ✅ Use a tool like WebhookPulse for real-time cross-provider alerting
